# Decisions: job-api

## Decided

- Milestone 2 is split into `job-api` first, then `email-job-execution` and `job-ui-crud` built in parallel on their own branches, both depending only on `job-api` (user)
- job-api is a thin API layer: contracts, job storage, public job routes, putting submitted jobs on the queue and the internal routes job-execution-service will call; it runs no jobs and has no UI (user)
- Carried over from `project-scaffold`: job-service is the only service with database access; job-execution-service changes job state only through job-service's internal update method under `/internal/v1`, protected by the service token and hidden from public docs (user)
- Carried over from `project-scaffold`: external cancel (from pending or scheduled) and retry (failed → pending) are built in `job-cancel` and `job-retry`, not here (user)
- No public field update in job-api: clients cannot edit a job's fields; the only update in this change is the internal one, through which job-execution-service changes status (and what goes with it) for the other changes; its spec is written so it states everything those changes will need (user)
- Delete: only finished jobs (completed, failed, cancelled) can be deleted, as a hard delete from the database; any other status answers a status conflict (user)
- Submit body in this change: type, payload, priority and max attempts, stored and returned; priority ordering and retries act on them in their own changes; scheduled time and idempotency key are added by `priority-scheduling` and `idempotency` (user)
- Email payload `{ to: email address, subject: non-empty string, body: string }`, email result `{ messageId: string }`; length limits are defined in the shared Zod schemas (see below) (user)
- The internal update covers the whole job lifecycle the roadmap needs, built and tested in this change: pending → processing (start), processing → completed (with result), processing → failed (with error), and a failed attempt sent back to pending for retry (decided by job-service, see below); later changes only call it (user)
- One internal route `PATCH /internal/v1/jobs/:id` whose body is a union keyed by the target status (with the fields that status needs); job-service checks that the transition is allowed (user)
- A queue message carries only the job id; the queue's entry id is `<jobId>:<attempt>`, so each attempt is queued once and a duplicate of the same attempt is ignored; the worker reads the job through `GET /internal/v1/jobs/:id`, so Postgres stays the source of truth (user)
- If a job is stored but putting it on the queue fails, the submit still answers 201 and the job stays pending; a later sweep re-queues pending jobs missing from the queue, built in `crash-recovery` (05-reliability); until then such a job stays pending. The trade-off goes into DECISIONS.md (user)
- On retry (failed attempt → pending) job-service puts the job on the queue again under the next attempt's entry id; if that fails, the job stays pending for the later sweep, the same rule as on submit (user)
- job-ui reaches job-service through a same-origin `/api` reverse proxy (job-ui's nginx in compose, the Vite dev server in development), so job-service needs no CORS; built in `job-ui-crud`, and the public routes must work behind that prefix (user)
- job-service owns the retry rule: the worker only reports `failed` with the error; job-service sets the job back to pending while attempts are below max attempts, otherwise to failed for good. In job-api the retry goes straight back to pending; backoff timing is added by `retry-backoff` (user)
- An attempt is counted on start (pending → processing), so a worker crash mid-job still uses up an attempt (user)
- The start report does not record which worker instance took the job; only the worker's logs carry its instance id (user)
- Query `GET /v1/jobs?limit&offset`: default and maximum limit from config, newest first by creation time, response `{ items, total }` (user)
- The list operation is called "query" everywhere (contracts, use cases, ports, specs) (user)
- Only the five base operations exist: create, get, query, update, delete, on the API and in every interface behind it (use cases and repository); no extra methods such as start, complete or fail: the lifecycle rules (allowed transitions, attempt counting, retry or final failure, re-queue) live inside the logic of update, and the finished-only rule inside delete (user)
- The query is backed by database indexes; which columns are indexed is decided in design (user)
- Public job routes live under `/v1/jobs`, matching the versioned `/internal/v1` prefix (user confirmed assumption)
- The job id is a UUID generated by job-service (user confirmed assumption)
- Every job response has the same shape: id, type, payload, status, priority, attempts (current and max), error, result, scheduled time, created/started/completed/updated timestamps; fields not used yet are `null` (user confirmed assumption, without progress)
- An unknown job id answers 404 with a new code `JOB_NOT_FOUND`; an operation not allowed in the job's current status answers 409 with a new code `JOB_STATUS_CONFLICT`, with the current status in `details` (user confirmed assumption)
- A submitted job answers 201 with the full job; delete answers 204 with no body (user confirmed assumption)
- The public routes appear in Swagger with their Zod-generated schemas (user confirmed assumption)
- Priority is an integer within a range (higher = more urgent) and max attempts an integer within a range; both have defaults when omitted (user confirmed assumption)
- The priority and max-attempts ranges and defaults and the email field length limits are defined once in the shared Zod schemas in `packages/contracts`, so job-service validation and the job-ui form use the same rules; they are not environment config (user; replaces "from config")
- Progress is not part of the Job: it belongs to a separate entity (batch-like), decided later in `batch-job`; job-api has no progress field and no progress update (user)
- When two start reports race for the same pending job, only the first succeeds; the second answers 409 `JOB_STATUS_CONFLICT` (the transition check is atomic in the database) (user confirmed assumption)
- Job type is a closed list that contains only `email` in this change; an unknown type or a payload that does not match the type answers 400 `VALIDATION_FAILED` (user confirmed assumption)
- The error stored on a failed attempt is `{ code, message, details? }` from the worker; result and error of the last attempt are kept on the job (user confirmed assumption)
- A query `limit` above the configured maximum answers 400 `VALIDATION_FAILED` naming the `limit` field (user)
- An id that is not a valid UUID answers 400 `VALIDATION_FAILED`; a well-formed id that matches no job answers 404 `JOB_NOT_FOUND` (user)
- The completed timestamp is set when a job reaches any final status (completed, failed for good, later cancelled) and is null while it can still run (user)
- An accepted internal state report answers 200 with the updated job, so the worker sees the resulting status (e.g. a failure turned into pending for retry) (user)

## Assumed

- [x] Public job routes live under `/v1/jobs`, matching the versioned `/internal/v1` prefix - one versioning scheme for both APIs
- [x] The job id is a UUID generated by job-service - opaque, safe to expose, usable as the queue's job id
- [x] Every job response has the same shape: id, type, payload, status, priority, attempts (current and max), error, result, progress, scheduled time, created/started/completed/updated timestamps; fields not used yet are `null` - one stable contract the execution and UI changes can build on
- [x] An unknown job id answers 404 with a new code `JOB_NOT_FOUND`; an operation not allowed in the job's current status answers 409 with a new code `JOB_STATUS_CONFLICT`, with the current status in `details` - follows the existing error body rules
- [x] A submitted job answers 201 with the full job; delete answers 204 with no body - common REST conventions
- [x] The public routes appear in Swagger with their Zod-generated schemas - Swagger is already decided as the API docs
- [x] Priority is an integer within a configured range (higher = more urgent) and max attempts an integer within a configured range; both have configured defaults when omitted - numbers stay in config
- [x] ~~Progress is an integer percentage 0-100 on the job~~ - rejected: progress belongs to a separate entity, decided later
- [x] When two start reports race for the same pending job, only the first succeeds; the second answers 409 `JOB_STATUS_CONFLICT` (the transition check is atomic in the database) - the basis for duplicate-free pickup later
- [x] Job type is a closed list that contains only `email` in this change; an unknown type or a payload that does not match the type answers 400 `VALIDATION_FAILED` - later job-type changes extend the list
- [x] Error stored on a failed attempt is `{ code, message }` (plus optional details) from the worker; result and error of the last attempt are kept on the job - enough for the UI and retry

## Open questions

- [x] List limit over the maximum, malformed ids, completed timestamp on failure, internal PATCH reply?
- [x] What does the retry re-queue use as the queue entry id, how does job-ui reach the API, and how does the form know the limits?

- [x] Update scope: what may a client change with the public update, and in which statuses? (`project-scaffold` decided the external update changes only status for cancel/retry, while the roadmap mentions updating jobs that have not started)
- [x] Delete: which statuses may be deleted, and hard or soft delete?
- [x] Submit: which fields does a client send in this change (type and payload only, or also priority, max attempts, scheduled time, idempotency key)?
- [x] Email payload and result: which fields?
- [x] List: pagination style, default order and the configured page size?
- [x] Queue message: does it carry only the job id (the worker reads the job through the internal API), or the whole job?
- [x] Submit consistency: what happens when the job is stored but putting it on the queue fails?
- [x] Internal API: one update route with a target status, or one route per lifecycle step (start, complete, fail)? Which transitions does job-service accept, and what does a rejected one answer?
- [x] Failure in this change: does a reported failure end the job as `failed` (retries and backoff come in `05-reliability`), and are attempts counted already?
