# Design

## Context

`GET /v1/jobs` goes through `JobsController.query` → `JobService.query` (applies the
configured default and maximum page size) → `JobRepository.query` (Prisma `findMany` and `count`
in one transaction, ordered `created_at DESC, id DESC`). The query string is validated by
`QueryJobsDto`, generated by `nestjs-zod` from `QueryJobsRequest` in `packages/contracts`, which
also feeds the Swagger docs. The `jobs` table already has `(status, created_at DESC)` and
`(type, created_at DESC)` indexes, added in `job-api` for these filters. Requirements: see
`specs/job-management/spec.md`.

## Goals / Non-Goals

**Goals:**
- Filters live in the shared contract, so job-ui (`job-list-filters-ui`) and other clients build the
  same query string the backend validates.
- One code path: the unfiltered query is the filtered query with no filters.

**Non-Goals:**
- No new indexes or migrations; no change to ordering, paging or the response shape.
- No changes to job-execution-service or job-ui.

## Decisions

### Contract: arrays normalised at the edge
`QueryJobsRequest` gains `status` and `type`, each optional. Express's query parser gives a string
for one occurrence and an array for repeated ones, so one shared leading step,
`z.transform(value => unique([value].flat()))`, turns either into a list without duplicates, and
each field pipes it into `z.array(JobStatus | JobType).min(1)`. Inner layers see a set of values.
An empty value (`status=`) becomes `[""]`, which is not a valid enum member, so it fails with an
issue for the field without special handling; an unknown value among known ones, an empty list or a
nested object fail the same way.

- Alternative: comma-separated values. Rejected by the user (decisions.md).
- Alternative: preprocess in the controller. Rejected: validation belongs to the shared schema,
  and the docs would not show the parameters.

Swagger: because the pipe starts with a transform, the generated docs show the field as an array
of the enum (`minItems: 1`), so the contract documents itself. A `z.union([string, string[]])`
first step was tried and rejected: the docs then showed `string | string[]` without the enum
values, and adding `@ApiQuery` on top does not help, because `cleanupOpenApiDoc` strips the merged
parameter's `type`.

### Domain and infra pass filters through unchanged
- `QueryJobServiceRequest` and `QueryJobRepositoryRequest` gain optional
  `statuses?: JobStatus[]` and `types?: JobType[]` (plural, since they are sets).
- `JobServiceImpl.query` passes them through after the existing limit checks.
- `PrismaJobRepository.query` builds one `where` (`status: { in }`, `type: { in }`, each only when
  given) and uses it for both `findMany` and `count`, so `total` counts the matching jobs. No raw SQL:
  this query needs no locking.

### Error handling
No new error code. Invalid filter values are Zod issues on the query DTO, mapped by the existing
validation pipe and filter to HTTP 400 `VALIDATION_FAILED` with an issue per field.

## Risks / Trade-offs

- [Express query parser changes to `extended` (qs) somewhere] → `status[]=x` or nested objects
  would arrive as other shapes; the schema rejects anything that is not a string or string array,
  so they fail as `VALIDATION_FAILED` instead of being misread. The e2e tests pin the repeated form.
- [Offset paging over a filtered set can skip or repeat rows while jobs change status] → same
  trade-off as the unfiltered list today; acceptable for the UI's polling list, noted in
  `DECISIONS.md`; cursor paging is planned as `job-list-cursor-paging` (milestone 7).
- [Index fit] → a single value per filter reads the matching index in `created_at` order (ties on
  `created_at` need a small incremental sort, since the index has no `id`); several values per
  filter fetch and top-N sort the matching rows; a combined status+type filter uses one index (or a
  bitmap AND) and filters by the other; `COUNT` reads every matching index entry; large offsets
  skip rows as today. All fine at the task's volume; the user chose no index changes here.
  `demo-seed` (milestone 7) measures them with `EXPLAIN ANALYZE`, and `job-list-sort-order` /
  `job-list-cursor-paging` redesign the indexes around the sort key.
